Release notes 0.2.0

OpenCanvas 0.2.0 release notes: the headless API, webhooks, the block SDK and editor profiles, upgrade notes, known limitations and the checklist.

Status: released 2026-11-25, tag v0.2.0 (tracker REL-04). Includes the block SDK runtime (BSDK-03/04), host editor profiles (EDP-01) and block discovery metadata. Licence: Apache-2.0 (ADR-037). Plan: docs/27. Acceptance: docs/23 §v0.2. Security audit: docs/18 §6.

OpenCanvas 0.2.0 makes the headless API the supported way for programs to read and write canvases. It also adds webhooks, version history and a block SDK. The host still owns users, permissions and files; OpenCanvas never stores documents (ADR-001). Support is best effort, with no SLA.

1. What 0.2.0 contains (frozen)

v0.2 = the stable headless API (docs/27 §4), the block SDK (§3), version history and webhooks (§0). The owner moved portable live blocks (§2, LIVE-01..06) to v0.3 on 2026-11-24. On 2026-11-25 the owner added host editor profiles and block discovery metadata.

Version 0.1.2 already shipped part of this work: HAPI-01..05 (the /api/v1 router, tokens, idempotency, cursors and rate limits, and the events stream) and version history. 0.2.0 makes them the stable contract and adds the rest.

2. Change control until the tag

  • Allowed: finishing BSDK-03/04, EDP-01 and block discovery metadata as designed, and P0/P1 fixes and security fixes. Each change has a tracker row, a test seen failing first and a CHANGELOG line.
  • Not allowed: new endpoints, new config or format changes outside those rows. They go to 0.2.1 or v0.3.
  • .ocanvas stays format version 1 and schemaVersion 1 (ADR-042). Additions are additive: extBlock, the ext root, history/ and requires.blocks.

3. Upgrade notes

The steps differ by the version you start from. Back up the database and the host files first. Let pending saves finish before you replace the server. Migrations run at start-up.

  1. Database migrations 0008 and 0009.
    • 0008_api_idempotency (new in 0.1.2) creates the api_idempotency table.
    • 0009_webhook_outbox (new in 0.2.0) creates the webhook_outbox table.
    • Both hold ids, counts, revisions and event JSON only, never document content.
    • Both run on SQLite, MySQL 8 and MariaDB 10.11. Redis-only storage uses keys instead.
    • Nodes that start together on an empty database now wait for each other's migrations (SEC-47). From 0.1.0 or 0.1.1 both migrations run; from 0.1.2 only 0009.
  2. New per-host config sections. All are optional. A host without them behaves as in 0.1.x.
    • [host.api]: user tokens (issuer, audience, all_files, token_admin), rate limits (rate_per_sec, burst, per-file writes) and default_mode. User tokens need OC_PUBLIC_URL or [host.api] audience.
    • [host.webhooks]: url (same origin as callback_base, checked at start-up), events, secret and max_attempts. Receivers verify X-OpenCanvas-Signature v2 and deduplicate by Idempotency-Key.
    • [host.versions]: history sources and the bounds of in-file history (docs/30).
    • [host.blocks]: enabled = ["type@range"] picks which installed SDK packages the host's editors see; the default is none. Packages are installed by the operator in OC_BLOCKS_DIR. OC_BLOCKS_ORIGIN must be a different site from OC_PUBLIC_URL.
    • [host.editor] (EDP-01): the editor profile. The default, full, behaves exactly like 0.1.x. A narrower profile hides blocks and features in the editor and never deletes content.

Start-up checks every section and refuses a bad value with a message that names it.

  1. The headless API is on by default (owner decision, 2026-11-25). /api/v1 answers for every host unless it sets [host.flags] api_v1 = false. It grants nothing new: every call needs the host key, which the 0.1 routes already accept, or a token of at most 15 minutes that the host signs itself, and user tokens stay off until the host sets a public base URL. The 0.1 routes (/v1/files/{id}/patch|commit|role|import|session, /v1/convert) keep working. They now carry a Deprecation header and a Link: rel="successor-version", and v0.3 retires them (docs/27 §9 decision 8), so on by default gives hosts the 0.2 line to move over.
  2. Editors older than 0.2 on documents with SDK blocks are closed with 4426. A 0.1.x editor deletes every extBlock it receives, because its schema has no such node. The room refuses that update and closes the session with code 4426 ("editor out of date: reopen the canvas"). Reloading the page loads the current editor. Hosts that cache the editor bundle or pin an old embed should reload it after the upgrade. Documents without SDK blocks are not affected.
  3. Room updates are checked against SDK block schemas (SEC-46). A client that writes attrs or data that break an installed package's schema gets a denial, as API and MCP writes already did.
  4. Container: ghcr.io/casualoffice/opencanvas:0.2.0. Helm: chart 0.2.0. WOPI hosts still need proof keys. For older deployments, read the v0.1.0 upgrade notes first.

4. Known limitations

  • No portable live blocks. They moved to v0.3 (docs/27 §2, docs/23 LIVE-A1..A7 deferred).
  • The categorised insert menu is a v0.2.1 follow-up. It uses [host.editor] profiles and block discovery metadata, and it is built after its prototype is approved (ADR-011). In 0.2.0 the existing slash menu shows what the profile enables.
  • Block SDK. No marketplace, and no install from the browser (v0.5). No third-party code runs on the server. Script migrations run only in the sandbox.
  • Headless API. No OpenCanvas-Version date header (decision 6). The MCP tool inputSchemas are still written by hand, not generated from the OpenAPI components. The Rust client has no yrs CRDT-sync feature; create_sync_token returns a ticket for any y-websocket client. Neither client is published to a registry (private / publish = false).
  • Open Low security findings (docs/18 §6), each with a recorded decision:
    • token grants allow exports of what the token can read;
    • the sync-ticket connect window counts from first use;
    • history caches are per room;
    • huge diagram coordinates become null;
    • SEC-36 and SEC-37 from v0.1.0.
  • Not demonstrated: scale-out across machines. Single node first; the room cap is 550 (docs/22).
  • AI and MCP are experimental and off by default.
