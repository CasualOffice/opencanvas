Integration guide

The host contract: register your host, sign a JWT launch token, embed the editor, answer load and save callbacks, and use postMessage and REST.

Status: draft v0.1, 2026-11-21. This is the contract an integrating application implements. Modelled on Collabora Online's WOPI integration (01 §4).

Golden rule: your application decides who may open which file with what role. OpenCanvas trusts that decision for the life of the token and enforces it on every edit. Your application stores the file.

1. Choose a handshake

Who verifies the userYou sign a JWTOpenCanvas calls your CheckFileInfo
Callbacks you implementGET file, PUT file, assets (people search and resolve optional)WOPI: CheckFileInfo, GetFile, PutFile
Extra round-trip on opennoneCheckFileInfo
Good forAny custom appNextcloud, ownCloud, Seafile-style hosts

2a. SDK block packages (BSDK-01, docs/27 §3, ADR-040, ADR-058)

Third-party blocks are installed by the server operator and enabled per host. There is no upload API and nothing is installed from the browser.

  • OC_BLOCKS_DIR: a directory with one sub-directory per package, each holding block.json (the manifest, docs/15 §4.2) and the bundle it names in entry. At start-up the server parses every manifest, checks it (type name, SemVer, JSON Schemas, templates, permissions, migrations) and verifies the bundle against integrity (sha384-<base64>, Subresource Integrity). A package that fails any check is refused: logged, listed on /healthz as blocks.refused[{package, reason}], and not installed. The server still starts; documents using its type keep the blocks as they are and show their fallback.
  • Type names are lowercase reverse-DNS labels (acme.okr, com.example.ticket-card); oc. is reserved for OpenCanvas's own blocks. One package per type.
  • OC_BLOCKS_ORIGIN: the separate origin block code runs on (https://blocks.canvas.example; http:// only for local development). Point a second host name at the same server; it answers /blocks/frame/{host}/{type} (the sandboxed frame document) and /blocks/{type}/{version}/{file} (bundle, migrations script, preview.png) only for requests to that host name, and 404 on the editor's. It must differ from OC_PUBLIC_URL's origin, or the server refuses to start. Without it no block code runs: editors show every SDK block as its read-only saved copy. Set OC_PUBLIC_URL too, so frames may be embedded only by the editor (frame-ancestors).
  • [host.blocks] enabled picks which installed packages a host's editors see, in that order. [host.blocks.permissions."<type>"] narrows what a block may do on this host: network keeps only the listed origins of the manifest's, members = "none" withholds the member list. A host can take permissions away, never add. The session (GET /v1/sessions/:ticket) lists the packages as blocks: [{type, version, v, title, icon, description, publisher, keywords, discovery, content, attrs, data, export, migrations, entry, frame, preview, integrity, permissions}] (frame is {OC_BLOCKS_ORIGIN}/blocks/frame/{host}/{type}, entry and preview live under {OC_BLOCKS_ORIGIN}/blocks/{type}/{version}/, all null without a block origin; permissions is the effective set). A host with no [host.blocks] gets an empty list.
  • The frame's CSP is default-src 'none'; script-src '<runtime sha384>' <package path>/; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src <effective network or 'none'>; base-uri 'none'; form-action 'none'; frame-ancestors <OC_PUBLIC_URL origin>; the bundle loads with its SRI hash. The editor frames it with sandbox="allow-scripts" only.
  • Validation of block attributes and data (docs/15 §4.2) uses every installed package, whatever a host enables, on .ocanvas load, the REST patch, imports, the headless API and MCP writes.

People (docs/21 revision 2): the @mention list is the people with access to the canvas, the same for every viewer. Everyone with access sees real names and the detail second line. OpenCanvas never shows or stores e-mail.

2b. Editor profiles (EDP-01, ADR-061; [host.editor])

One engine, many experiences. A profile decides which blocks the editor offers to insert; features turn whole surfaces off. Omit the table for today's behaviour (full).

[host.editor]
profile = "meeting"          # notebook | meeting | project | diagramming | document | full (default)
allow_profile_switch = false # reserved: stored and sent, no UI yet
intents = true               # INS-01: goal chips in the insert menu (default true)
chips   = ["Track tasks", "Plan a sprint", "Draw architecture"]  # replaces the built-in chips

[host.editor.blocks]         # optional

quick_insert = ["core.checklist"]  # the insert menu's Quick insert tiles, in order; default []

[host.editor.features]       # every key optional
comments        = true

diagramming     = true
templates       = true

Block ids. core.text, core.heading, core.checklist, core.bulleted_list, core.numbered_list, core.toggle, core.quote, core.callout, core.divider, core.code, core.database, core.kanban, core.calendar, core.table, core.spreadsheet, core.chart, core.image, core.file, core.date, core.link_preview, core.embed, core.whiteboard, core.diagram, core.shapes, core.columns, core.import, core.assistant. kanban and calendar are views of a database and insert through the Database entry; diagram and shapes are modes of a whiteboard and insert through the Whiteboard entry. The insert menu (INS-01, ADR-062). "/" (and the gutter and phone "+") opens one menu: Quick insert (quick_insert, else Text, Heading, List, Image, Table; at most five; an id like core.checklist or core.kanban inserts that variant), Recent (this browser only), Start from a goal (the goal chips) and Explore (Content, Data & planning, Visual & diagrams, Layout, Extensions). 2c. Portable live blocks (LIVE-01, docs/27 §2, docs/34 §2, ADR-039, ADR-069, ADR-070)

A live block is written once and shown live in many canvases: its content is its own host file (a small .ocanvas with meta.kind = "live"), embedded by file id and opened as its own room. You keep that file like any other, under your ACL; OpenCanvas stores nothing new.

[host.flags]
live_blocks = true                         # off by default in 0.3.0-alpha

[host.live]
snapshot = "title"                         # "none" | "title" (default) | "content": what of a live
                                           # file the canvases that embed it may keep (§2c below)
link     = "https://app.acme.example/files/{fileId}"   # optional: exports link a live block here
max_open = 8                               # 1-8: live block rooms one editor session may have open

You implement two callbacks (§5): **POST /files (create the backing file for "Make live"; without it "Make live" answers 501 and the editor hides it) and POST /access, which is required** for live blocks: every person who meets a live block is checked against it (cached 30 s). Without /access, only the files your launch token lists in live open, and only read-only.

  • Who may make and embed. The token's perms.live (default false) lets a person make live blocks and insert liveBlock/blockRef nodes; the room refuses such an insert from anyone else.
  • Derived grants. When an editor meets a live block it asks POST /v1/live/session {ticket, fileId}: the canvas must really embed that file, then your /access answer decides the role (none: 403, nothing about the file is shown) and its optional path is what the block's header shows as where the source lives. The new session expires with the parent, has the parent's perms at most (never live), and cannot derive again. It is an ordinary room session: your role API (§7) and revocations reach it at once.
  • Snapshots. snapshot = "title" keeps only the title in the embedding canvas; "none" keeps not even that; "content" (for hosts whose ACL treats embedding as sharing) also keeps a Markdown snapshot (≤ 64 KB), written by the server, never by a client. Exports inline what the exporting person can read and show "Live block: <title> (no access)" for the rest.
  • Depth. A live file cannot contain live blocks or references, and a canvas holds at most 50.
  • Usage. OpenCanvas keeps no index of where a live block is used: the live.embedded and live.removed events (§7b, webhooks §7c) tell you, so you can keep your own.
  • Deleted files. Answer /access with 410 (or {"role": "none", "gone": true}) for a live file you deleted or moved: the block then says "This live block was deleted or moved" and offers Remove (and, under snapshot = "content", Keep last copy). A plain none reads as "no access".
  • In the editor (LIVE-03, ADR-069). The session answer's live says what to offer ({enabled, make, insert, snapshot, maxOpen, link}). "Make live…" is in the block menu; "Live block" in the insert menu asks your picker (UI_PickLiveBlock, below): OpenCanvas keeps no list of live files. Pasting a block link (the editor's own "Copy link", or a URL matching [host.live] link, with #block=<id> for one block or #live for a live file) asks Live block / Reference / Link. A live block shows an always-visible header (Live mark, title, the people in it, Open source, options) and is edited in place; references refresh on their own.
  • Who can see this. GET /v1/live/audience?ticket&fileId counts the canvas's other members (your members callback, else the token's members; at most 200) that your /access would not let open the live file. One /access call per member per 30 s; never names.

Start-up checks. A live_blocks that is not a boolean, an unknown [host.live] key, a bad snapshot, max_open outside 1-8, a link that is not http(s) or lacks {fileId}, and live_blocks = true on a WOPI-only host, a temporary-canvas host or a host without callback_base refuse to start, naming the host.

2c-bis. Partial sync (PSYNC-02/03, ADR-076; [host.flags] partial_sync)

[host.flags]
partial_sync = true    # the default from 0.4; false keeps every room whole

A room keeps each database and board (diagrams included) as a subdocument that the editor loads when the block comes near the screen, so a large canvas opens on its text and the server and the browser hold only what people look at (on the 50 MB benchmark canvas the room holds the main document: 220 MB against 4.4 GB for 20 viewers, and the browser 16 MB against 472 MB). Your files do not change: every save is the same .ocanvas format v1 with the same content and Yjs item ids, and the API, MCP, exports, search.json and history read and write as before. It works on every storage (SQLite, MySQL/MariaDB, the Redis WAL, Redis only) and under either durability; a part's edits reach the WAL as they happen.

Editors before 0.4 do not speak it: a split room closes them with 4426 and they show "reopen the canvas", which loads the current editor. If you embed an older editor build, or run a client that edits the Y.Doc directly without caps=subdoc, set partial_sync = false until it is updated. Turning it off again is safe: a room folds its parts back into one document when it next opens. Temporary canvases and live block files are never split.

2c-ter. Formulas, relations and rollups (DB4, ADR-078; [host.flags] formulas)

formulas = true lets people add formula, relation and rollup fields to databases (off by default; the session JSON carries formulas). Fields that already exist always compute, whatever the flag. Only expressions and related row ids are stored in the canvas; the server computes the values for exports (Markdown, HTML, CSV, PDF), search.json, the API and MCP (queryRows / db_query return them, and filters and sorts see them). Errors are values ({err: "#DIV/0", msg} in JSON, the code in text exports). Relations across canvases go only through a live block already on the canvas, are one-way, and show "No access" to readers without access to the live file.

2d. Offline copies (OFF-01..08, docs/34 §3, ADR-063, ADR-064; [host.offline])

A person can keep a canvas on their own device and keep editing without a network; the edits merge when they are back. The copy lives only in that browser (IndexedDB, encrypted under a device key per host and person); OpenCanvas stores no content for it (ADR-001): the server keeps one number per host and person (the revocation generation). Off by default at both levels: you turn it on for the host, you allow it per launch, and the person turns it on per canvas.

[host.offline]
enabled      = true       # default false; JWT hosts only in v0.3 (WOPI hosts refuse to start)
auto_recent  = 0          # >0: also keep the last N opened canvases without asking (0-50)
grant_days   = 7          # how long a copy opens without reconnecting, 1-30
max_role     = "edit"     # edit | comment | view: the highest role a copy keeps
max_canvases = 50         # per person per host per device (1-500)
max_mb       = 200        # all copies of one person on one device (1-2000)
uploads_mb   = 50         # queued uploads per canvas (and at most 20 files)
unsent_mb    = 5          # unsent changes per canvas before editing pauses (1-50)
  • Per launch. The token's perms.offline (default false) says whether this person may keep this canvas offline now. Leave it out on shared devices, kiosks, guest and "don't keep me signed in" sessions; the optional top-level offlineReason (for example "shared-device", ≤ 200 characters) is shown where "Available offline" would be.
  • The grant. When both allow it, the session answer carries offline.grant: an ES256 JWS the server signs (host, sub, file, role ≤ max_role, exp ≤ grant_days, gen). The editor keeps it with the copy and uses it only on the device, to decide whether and in which role the copy opens. It is never a credential: reconnecting is always a fresh launch through you (POST /tokens/refresh, §5), and your current answer decides. The signing key comes from OC_OFFLINE_KEY (base64 of 32 random bytes) or is derived from OC_KEK, so every node agrees.
  • Revoking. POST /api/v1/offline/revoke {"userId"} (host key or canvas:admin, §7b) raises the person's generation: every device holding their copies for your host deletes them, with their unsent changes, at the next session answer. A lower role on reconnect holds the changes (download or discard); no access deletes that copy.
  • Signing out. Your sign-out page must clear the device, below (§4c).

Start-up checks. An unknown [host.offline] key, a value out of range, a bad max_role, auto_recent above max_canvases, and enabled = true on a WOPI-only host refuse to start, naming the host.

2e. Automation (AUTO-01..07, docs/34 §5, ADR-067, ADR-068; [host.automation])

Rules such as "when Status changes to Done, move the row to Archive and notify the owner" are stored in the canvas (the automations root, additive to format 1), so you store them with the file and they travel with copies (a copy's rules are switched off and ownerless). The OpenCanvas server runs them as the collaborator "Automation" on behalf of the person who last saved or switched on the rule, re-checking that person's role with your POST /access at every run (cached 30 s): below edit, the rule pauses. Without /access, the owner must have opened the canvas in the last 30 days. Automation is off until you add the table:

[host.automation]
enabled          = true
actions          = ["field.set", "row.move", "todo.set", "todo.add", "comment.add", "notify", "http.post"]
allow_origins    = ["https://ci.acme.example"]  # URL calls may reach these besides your callback origin
max_rules        = 25      # per canvas, at most 100
runs_per_minute  = 60      # per rule
runs_per_day     = 1000    # per canvas
max_changes      = 50      # per run
max_depth        = 3       # rules started by rules
min_interval_min = 15      # schedules
time_zone        = "Europe/Berlin"   # IANA name, UTC, or UTC+05:30; rules may name their own
  • Who may create rules: editors whose launch token has perms.automate: true (default false). Others see the rules read-only; the run history is shown to editors only. The server refuses a client write to automations without it, an invalid rule, an action you did not allow, a URL on another origin, and an enabled rule not owned by the person saving it.
  • Automation needs a database (SQLite, MySQL or MariaDB) for its schedule and run log; with Redis-only storage the server refuses [host.automation] at start-up. Both tables hold ids, times, counts and codes, never canvas text; runs are kept 30 days.
  • Date and schedule rules run with nobody in the canvas. A worker on every node claims due rows (one node per slot) and opens the file the way the API does: GET and PUT /files/{fileId} arrive with no bearer token, signed (v2) as always. Treat such a signed call as your own service acting for the file. A file that does not load is retried every 5 minutes for an hour, then the run is logged as failed.
  • **notify** calls your POST /mentions (§5) with by: "automation:<ruleId>", onBehalfOf: <owner id>, mentioned, excerpt (the rule's message) and automation: {ruleId, name, runId}, with no bearer token. OpenCanvas sends no mail.
  • **http.post** sends {rule: {id, name}, runId, fileId, by, trigger, fields, at} (only the fields the rule names) to your callback origin or an allow_origins origin, signed like webhooks (X-OpenCanvas-Signature v2 with [host.webhooks] secret or your callback secret, X-OpenCanvas-Event: automation.url, Idempotency-Key: <runId>), 10 s timeout, no redirects, 3 tries (now, after 1 minute, after 10 minutes; a 3xx or 4xx other than 408/425/429 is final).
  • Ten failed runs in a row pause a rule and notify its owner once. Events automation.ran and automation.failed go to the events stream and webhooks; edits by a rule carry by: "automation:<ruleId>", and the save's X-OpenCanvas-Authors lists automation:<ruleId>.
  • Rules are document data: anyone who can read the file can read every rule, its owner, its URL targets and the fields it sends. Never put secrets in a rule.
  • API and MCP: GET/PUT/DELETE /api/v1/files/{fileId}/automations[/{ruleId}], POST …/automations/{ruleId}/enable, POST …/automations:test, GET …/automations/runs (§7b); MCP canvas_automations, canvas_automation_save, canvas_automation_enable, canvas_automation_test.

2f. File types and app mode (FTY-01..08, docs/40 §0.8, ADR-085)

A host may give each file a type. A document is today's canvas, where any blocks mix. A spreadsheet, whiteboard or database file holds exactly one root block of that kind and opens in app mode: the editor renders that block full-page with its own chrome, with no document title, page margins, gutter or insert menu.

file.typeRoot blockApp mode chromeExports offered first
document (default)any blocksthe canvas editorper export_formats
spreadsheetcore.spreadsheettoolbar, formula bar with the cell name, the grid edge to edge, sheet tabs, selection sum/average/countxlsx, csv, pdf
whiteboardcore.whiteboard (diagram mode is a switch on the board)tools, board bar (Sketch / Diagram, shapes, frames), zoom, minimappng, svg, pdf, drawio

  • Telling us. Put file.type in the launch token (§3). Any other value is refused at launch with 400 TYPE_INVALID. GET /hosting/capabilities lists fileTypes; a server without it ignores the claim and opens a document, so check it before you show typed New entries.
  • New files. When your load callback answers 404 (a new file) for a typed launch, the server creates the root block as the file's first edit (an empty sheet Sheet1, an empty board, a database with one Table view) and saves it through your PUT /files/{fileId} like any edit. start (ADR-048) is ignored in app mode.
  • The file remembers. The .ocanvas manifest carries type (additive to format 1; older readers ignore it). A launch without the claim uses the manifest's type, so a downloaded spreadsheet reopens as one in any host. The claim wins when both are present.
  • Never lose content. If a typed launch meets content that is not exactly one root block of that kind (someone added a paragraph through the API, or the host typed an old document), the editor opens it as a document with a notice ("This spreadsheet has other content, so it opened as a document") and the session answers app: "document", appFallback: "content". Nothing is removed or rewritten.
  • Session answer (docs/15 §2): app (document | spreadsheet | whiteboard | database). Profiles (§2b) apply to documents and to database row pages; app mode has no insert surfaces to filter. [host.editor.features] apply as usual (comments on cells and shapes, version history, AI, import).
  • Everything else is the same file. Version history (§5a), search (search.json gains type), exports, the headless API (GET /api/v1/files/{fileId} and /extract answer type), MCP, webhooks, live blocks and offline copies treat a typed file exactly like a document. export in app mode with no format picks the first of the table's formats that export_formats allows.
  • From a block to a file. In a document, a spreadsheet, whiteboard or database block offers Expand (fills the editor for a while; still the document) and Make a spreadsheet file (or whiteboard, database). 5a. Version history (VH-01, docs/30, ADR-051, ADR-055)

Two sources, chosen in [host.versions] (§2):

  • Your versions. Every save you receive is a complete .ocanvas, so every save is a version. JWT hosts implement List versions and Get version (§5) and set [host.flags] history = true. WOPI hosts advertise OpenCanvas_SupportsVersions: true in CheckFileInfo and answer GET {WOPISrc}/versions?access_token=[&cursor=] (the JSON of §5) and GET {WOPISrc}/versions/{v}/contents?access_token= (bytes), both proof-signed like every WOPI call. Without them we link to your own page (history_url, or CheckFileInfo FileVersionUrl; with FileVersionPostMessage: true we post UI_FileVersions to your page instead).
  • In-file history (ADR-055): a bounded set of earlier versions kept inside the .ocanvas itself, as compressed reverse diffs. On by default for JWT hosts; turn it off when deleted text must not travel with the file. Temporary canvases have none.

Retention is yours: we never delete one of your versions and never ask you to. A named version is an ordinary save with X-OpenCanvas-Autosave: 0 and the name; restore is an edit in the live room followed by a save named "Restored from …". We keep nothing in our database: versions are read on demand and cached in memory for 5 minutes.

The session answer (docs/15 §2) carries history (full | link | none), historySource (host | file, the list shown first), historyHostName (for "Kept by …"), historyUrl and historyPostMessage (link mode), and the effective perms.history, perms.restore and perms.commitMessage.

7. Server-to-server REST (you → us)

Use X-OpenCanvas-Key: <api_key> + X-OpenCanvas-Host: <host id>.

  • Revoke or downgrade a user live when you change ACLs: POST /v1/files/{fileId}/role {"userId":"u_123","role":"view"} — the user's open session switches to read-only immediately (or is closed with "role":"none"). Roles: view | comment | edit | none. Answers 200 {"connections":1,"sessions":2} (live connections switched, tickets updated); 401 API_KEY_INVALID for a wrong host/key, 400 ROLE_INVALID. The role also applies to launch tokens issued before the call (by their iat): an older token opens with this role, and with "role":"none" it is refused with 403 ROLE_REVOKED. Tokens issued after it, or without iat, use their own role. "role":"none" also takes the user out of the canvas's member list at once (the cached members answer is dropped, open editors refetch it, and an older token's members no longer counts for them) until you grant access again or they open the canvas with a new token.
  • Member list changed (someone added or removed outside a role call): POST /v1/files/{fileId}/members/invalidate → 200 {"invalidated":true}. Drops the cached members answer; open editors refetch /v1/members. Same headers as every call here.
  • Patch content from a bot: POST /v1/files/{fileId}/patch (see 04 §6) with {"ops":[…],"author":{"id","name"}}. Ops: append, insertAfter{blockId}, replace{blockId}, delete{blockId}, each with markdown or Tiptap blocks. Blocks are addressed by their blockId attribute; the answer lists the ids of the blocks you inserted ({"applied":2,"blockIds":["b_…"],"live":true}). If nobody has the file open we load it from you, apply and save straight away (the answer then carries version). Send X-OpenCanvas-Callback-Token: <token> if your callbacks need a bearer for that load/save.
  • Force save before you snapshot/backup: POST /v1/files/{fileId}/commit → 200 {"live":true,"saved":true,"version":"18"} once your PUT answered, 202 {"queued":true} if it failed and will be retried from the outbox, 409 on a conflict.
  • Close everything (file deleted/moved): DELETE /v1/files/{fileId}/session — a final save, then every connection is closed and every ticket for the file is dropped. 200 {"closed":true,"sessions":3}.
  • Import into a canvas (docs/23 FC-10): POST /v1/files/{fileId}/import?format=md|html|csv&author=<userId>[&authorName=][&blockId=][&name=] with the file as the raw body (UTF-8, ≤ 5 MiB). Markdown and HTML become blocks; HTML keeps only http(s), mailto:, relative and # links and http(s)/relative/data:image/ image sources, and drops scripts, styles and event attributes. CSV becomes one database block (first column the title; other columns typed number, date YYYY-MM-DD, checkbox true|false|yes|no, select for ≤ 20 repeated values, else text), ≤ 10,000 rows and ≤ 200 columns (413 IMPORT_TOO_LARGE). It lands after blockId, or at the end, as one change. Needs the format in [host.flags] import_formats (else 403 IMPORT_OFF); the operator's OC_IMPORT=off refuses every import. Answers {"format","blockIds",…,"live"}, plus version when nobody had the file open (saved straight away, like patch). Editors use the same with a session: POST /v1/import?format=&ticket= (edit role only); the session response carries import.formats so the editor shows the entry only when allowed.
  • Diagram files (DGM-15, docs/29 §7): format=drawio (.drawio, diagrams.net .xml, compressed pages too) and format=excalidraw, same 5 MB limit and gate. dryRun=1 converts and answers {"format","dryRun":true,"report"} without changing anything; report is {pages, page, counts: {shapes, connectors, images, containers, needLook}, items: [{level: warn|gray|ok, code, title, detail?, count, examples}]}, most important first. page=<n> (0-based) picks a draw.io page. The import adds a board block after blockId (or at the end), or adds to an existing board with boardId= (to the right of its shapes), and answers {"boardId","blockIds","shapeIds","shapes","connectors","report"}. Unreadable, too deep, too large after decompression or entity-declaring files get 400 IMPORT_INVALID / 413 IMPORT_TOO_LARGE with a plain-words reason. Nothing is ever fetched from a file.
  • Spreadsheets (SHEET-03, ADR-080): format=xlsx or format=ods, same 5 MB limit and gate, become one Spreadsheet block (every sheet, values and formulas as typed; at most 200,000 cells, number formats and styles not yet kept) after blockId or at the end, and answer {"format","sheets","sheetId","blockIds"}; an unreadable file gets 400 IMPORT_INVALID. Markdown, HTML, Word, search.json, GET …/blocks/{blockId} (sheet.sheets[].rows) and MCP canvas_read show a Spreadsheet block as tables of the values the grid displays, computed on the server.
  • Add your own icon (DGM-17, ADR-057; editor session, edit role): POST /v1/icons?ticket= with an SVG or PNG as the raw body (≤ 256 KB; 20 uploads a minute per person, else 429). The server cleans it: SVG without DTDs, ≤ 2,000 elements, nesting ≤ 16, normalised by usvg (scripts, event handlers, foreignObject, outside references and editor metadata removed), ≤ 64 KB cleaned; PNG checked by its magic bytes, ≤ 1024 px a side, re-encoded. dryRun=1 answers {"format","width","height","bytes","removed":[{"what","count"}],"dataUrl"} and stores nothing; with name= (and keywords=a,b) the cleaned icon is written into the document's icons root and the answer adds "id"; replace=<id> swaps an existing icon's file. Refusals are 422 {"code","message"} (unsupported, invalid_svg, invalid_png, dtd, too_many_elements, too_deep, png_too_large, cleaned_too_large, empty, limit) or 413 (too_large). POST /v1/icons/:id?ticket= with {"name","keywords"} renames, with {"remove": true} removes. Limits: 200 icons and 1 MB of icons per document. Only the server writes icons; a client update touching it is refused. Nothing is ever fetched from a file.
  • Stateless conversion: POST /v1/convert?from=md|html|ocanvas&to=ocanvas|md|html|json|docx|pdf with the file as the raw body. DOCX and PDF embed images only from your callback_base origin (fetched signed) or an asset_origins entry (plain GET) — no redirects, ≤ 10 MB, image/* only; other images become links. Boards become pictures (PNG in DOCX, SVG in HTML/PDF). to=pdf needs the operator to run the Gotenberg sidecar (OC_PDF_RENDERER), else 501.

7a. MCP endpoint (AI-01, ADR-032; off by default)

Turn it on per host with [host.ai] mcp = true, and give it a public URL: OC_PUBLIC_URL, or [host.ai] mcp_audience for this host. Without one, MCP stays off (404) and the server logs a start-up warning; the audience is never taken from the request's Host header. External MCP clients and your own agents call POST /mcp/{hostId} (streamable HTTP, stateless, one JSON-RPC message per POST, JSON answers; MCP 2026-07-28, and 2025-11-25 by version negotiation). Methods: initialize (server/discover), ping, tools/list, tools/call, resources/templates/list, resources/read (canvas://{hostId}/{fileId} Markdown, ….json document JSON). Role source. If you implement the optional POST /access callback (§5), OpenCanvas asks it for the user's role on each file an MCP call touches (cached 30 s) and ignores the token's role claim; none refuses every tool. Without it, the role claim is trusted, but only for the files the token lists in files: a token without files is refused (ROLE_FORBIDDEN, FILES_REQUIRED: …). Setting [host.ai] mcp_all_files = true lifts that and lets one token's role apply to every file of the host; it is broad, so prefer files or /access (SEC-34).

The effective permission is min(scope, role): canvas:write does not let a view user write, and a canvas:read token does not let an editor write. A request without a valid token gets 401 with WWW-Authenticate: Bearer resource_metadata="https://<opencanvas>/.well-known/oauth-protected-resource/mcp/{hostId}"; that RFC 9728 document names your mcp_issuer as the authorization server. Tokens are never forwarded to you; callbacks stay HMAC-signed. MCP calls take from the same per-user bucket as the headless API (§7b; default 10 requests/s, burst 30, [host.api] rate_per_sec / burst; [host.ai] mcp_rate_per_min still sets the rate when [host.api] does not), then 429 with Retry-After.

Tools (each takes fileId): canvas_read, canvas_find, db_describe, db_query, board_read, comment_list, members_list (read); comment_add (comment); canvas_patch, db_upsert_rows, db_create, db_add_field, board_add_shapes (write). Each tool is an adapter over the §7b operation it stands for (HAPI-08; docs/24 §5.3 lists them) and answers what that operation answers, wrapped as untrusted data for reads. A write also takes from the file's write bucket shared with the API, and may carry "_meta": {"idempotencyKey": "…"} in its tools/call params: the API's idempotency store then replays the stored result for 24 h (_meta.idempotencyReplayed: true) and refuses the key with other arguments (IDEMPOTENCY_KEY_REUSED). Edits are live Yjs transactions, broadcast and autosaved like a person's. Canvas content comes back wrapped as untrusted data. Changes to existing blocks carry ifMatch (the block rev from a read; a mismatch returns STALE_BLOCK with the fresh block). By default new content lands directly and changes to existing content become suggestions (stored in the file's suggestions root for a person to accept in the editor); [host.ai] default_mode = "direct" changes that. Deleting more than 5 blocks needs confirm: true. Member lists never carry e-mail addresses. Errors are tool results with isError: true and a code.

7b. Headless API v1 (HAPI, ADR-041; on by default, [host.flags] api_v1 = false turns it off)

The supported API for programs: bots, integrations, back-office jobs. The website has the full reference, generated from the OpenAPI document: API reference. It is described by an OpenAPI 3.1 document served at GET /api/v1/openapi.json (checked in as crates/oc-server/api/openapi.json; a contract test keeps it and the router identical). On by default from 0.2.0 (it was off in 0.1.2); turn it off per host with [host.flags] api_v1 = false, and every /api/v1 call for that host answers 404 API_OFF. Every call still needs the host key or a token the host signed. The path major changes only for breaking changes; within v1 changes are additive.

Auth, two kinds, one check (shared with MCP, §7a):

  1. Host key, server to server, as in §7: X-OpenCanvas-Host + X-OpenCanvas-Key (full access to your files, admin operations included). Optional X-OpenCanvas-Author: <userId> attributes changes to that user (edit origin api:<userId>; default svc:<hostId>); X-OpenCanvas-Callback-Token is passed on callbacks as in §7.
  2. User-scoped bearer token (Authorization: Bearer <jwt>) for code acting for one of your users. You mint it; OpenCanvas never issues user tokens. Same keys as launch tokens (HS256 secret, PEM or JWKS), same claims as MCP tokens:

| claim | value | |---|---| | iss | your host id, or [host.api] issuer (must be unique among hosts) | | aud | {[host.api] audience or OC_PUBLIC_URL}/api/v1. Without a public base URL (OC_PUBLIC_URL or [host.api] audience) user tokens are off for the host (401 TOKEN_INVALID); the audience is never taken from the request. Writes land in the live room as one Yjs transaction, broadcast to editors and autosaved to you like any edit (open the file with POST …/commit when you need it saved now). Changes to existing blocks land directly unless the call sends "mode": "suggest" or the host sets [host.api] default_mode = "suggest". Deleting more than 5 blocks needs "confirm": true.

Paging. GET …/blocks (≤ 100 per page) and GET …/databases/{dbId}/rows (≤ 200) answer {…, has_more, next_cursor} and, when more follow, Link: <…?cursor=…&limit=…>; rel="next". Cursors are opaque and signed: pass them back unchanged. They are bound to the file (and, for rows, the database, filter, sort and fields) and last an hour (410 CURSOR_EXPIRED; anything else wrong is 400 CURSOR_INVALID). A block cursor is a Yjs relative position after the last block returned, so paging survives concurrent edits: a block inserted or deleted before it does not shift the next page, and if that last block is deleted the next page starts at its successor. Every block that exists for the whole walk is returned exactly once.

Rate limits. One token bucket per caller (the host key, or a token's sub), shared with MCP: default 10 requests/s, burst 30; and one per file for writes (POST/DELETE): default 5/s, burst 10. Every answer carries RateLimit-Policy: "subject";q=30;w=3 (plus "file-writes";q=10;w=2 on writes) and RateLimit: "<bucket>";r=<remaining>;t=<seconds to full>; an empty bucket answers 429 RATE_LIMITED with Retry-After. Set them per host in [host.api]: rate_per_sec, burst, file_writes_per_sec, file_burst. With Redis (cluster, hot WAL or Redis-only storage) the buckets are shared by every node.

Idempotency. Every POST /api/v1/files/… accepts Idempotency-Key: <1-255 visible ASCII>. The key is yours per user (host key + X-OpenCanvas-Author, or the token's sub). A repeat of the same request answers the stored result with Idempotency-Replayed: true for 24 h; the same key with another body is 422 IDEMPOTENCY_KEY_REUSED; a duplicate that arrives while the first still runs, on any node, is 409 IDEMPOTENCY_IN_PROGRESS with Retry-After: 1. Failed requests are not stored, so a retry runs again. Keys live in the database (api_idempotency) or, in Redis-only mode, in Redis (oc:idem:…), with request hashes and write answers (ids, counts, revisions) only, never document content. POST /api/v1/convert returns a document and takes no key (it changes nothing).

Resume after a disconnect with Last-Event-ID: <id> (or ?since=): the server keeps the last 512 events of each file in memory and answers those after your id, or one resync (whose id is the newest event it has) when your id is gone (evicted, server restarted, another node that was not listening). ?types=saved,commented filters. In a cluster the room's owner publishes each event on the members bus, so a stream on any node gets them. A stream that falls 256 events behind is closed: WebSocket close code 4008, SSE a final event: close with {"code":4008,"reason":"…"}; reconnect with your last id. With a user token the stream closes with 4001 when the token expires and with 4003 once the host revokes the user (POST …/role {"role":"none"}); nothing is sent after the revoke. At most 100 streams per file on one server (429 TOO_MANY_STREAMS). Behind nginx, X-Accel-Buffering: no is set; keep proxy read timeouts above 15 s.

CRDT sync (HAPI-05). The session ends at expiresAt, at most 15 minutes and never after the token's exp; ask for a new ticket to continue. The answer is a credential: Cache-Control: no-store, no Idempotency-Key (the same key gets a fresh ticket). Awareness is optional; if you send it, your entry is stamped with your user like any client's.

Errors are RFC 9457 application/problem+json: {"type":"urn:opencanvas:problem:stale-block","title":"Precondition Failed","status":412,"detail":"…","code":"STALE_BLOCK","fresh":{…}}. The code is the same machine code the 0.1 routes use (BLOCK_NOT_FOUND, STALE_BLOCK, ROLE_FORBIDDEN, PATCH_INVALID, DOC_TOO_LARGE, CONFLICT, CONFIRMATION_REQUIRED, …). Statuses: 400 bad input, 401 no or wrong credentials, 403 role or scope, 404 unknown file part, operation or API_OFF, 409 conflict or confirmation, 412 a stale ifMatch / If-Match (with fresh), 413 too large, 503 retry (Retry-After).

The 0.1 routes (/v1/files/{id}/patch|commit|role|import|session|members/invalidate, /v1/convert) keep working unchanged through 0.x, with or without api_v1, and keep their {"error":{"code","message"}} shape. They now carry Deprecation: @1795478400 (RFC 9745, 2026-11-24) and Link: </api/v1/…>; rel="successor-version"; they are retired in v0.3.

7c. Webhooks (WH-01, ADR-056; [host.webhooks])

OpenCanvas POSTs the change events of §7b to one URL of yours, so you can react without holding a stream open (index a saved file, notify on a comment). Off unless the host entry has a [host.webhooks] table:

[host.webhooks]
url          = "https://host.example.com/opencanvas/hooks"  # must be on your callback_base origin
events       = ["saved", "commented", "mentioned"]          # or ["*"]; see the §7b event table
# secret     = "env:OC_WEBHOOK_SECRET"                      # default: callback_secret, else jwt_secret
# max_attempts = 12                                         # 1-20

Request. POST <url> with the event as the body ({"id","type","fileId","at","data"}, the same JSON as the events stream: ids, user ids, versions and counts, never document text) and the headers Content-Type: application/json, X-OpenCanvas-Event: <type>, X-OpenCanvas-Event-Id: <id>, Idempotency-Key: <id>, X-OpenCanvas-Delivery-Attempt: <n> and X-OpenCanvas-Signature: t=<ts>,v1=<hex>,v2=<hex>, signed exactly like callbacks (§5): verify v2 = HMAC-SHA256(secret, "<ts>.POST.<path?query>.<body>") in constant time and reject timestamps more than 5 minutes off. <ts> is the time of the attempt, so a retry carries a new signature. No bearer token is sent.

Delivery. Answer any 2xx quickly (10 s timeout) and do the work afterwards. Network errors, timeouts, 408, 425, 429 and 5xx are retried after 10 s, 30 s, 1 min, 5 min, 15 min, 30 min, 1 h, 2 h, 4 h, 8 h, then every 12 h (a longer Retry-After in seconds, up to 12 h, wins), until max_attempts (default 12, about a day); then the event is dropped (gave_up in the metrics). Any other 3xx or 4xx drops it at once: redirects are never followed. Delivery is at least once: deduplicate by Idempotency-Key. Order is not guaranteed across retries; use at and the id (a ULID) to order events of one file. Events are written to a database outbox (webhook_outbox) by the server that runs the file's live room before they are sent, so they survive restarts and are sent by exactly one server of a cluster; an event can be lost only if that server dies in the moment between the change and the outbox write. Webhooks need a database (SQLite, MySQL or MariaDB): with Redis-only storage the server refuses to start with [host.webhooks].

Where it may point (SSRF). The URL must be on the same origin (scheme, host, port) as your callback_base; anything else stops the server at startup and is refused again before every delivery. With OC_CALLBACK_BASE_OVERRIDE, a URL on the configured origin is sent through the override, like callbacks. To receive webhooks on another domain, relay them from your callback origin.

Metrics. oc_webhook_deliveries_total{host,result} (ok, retry, rejected, gave_up, refused) and oc_webhook_delivery_seconds{host} (time of one attempt), on the OPS-01 dashboard's "Webhooks" row.

8. Lifecycle & guarantees

  • One live room per (host, file). Users who open the same file join the same room — there is no fork. The room loads your file once.
  • Your file is updated by commits only. Autosave commits are flagged X-OpenCanvas-Autosave: 1 so you can collapse them in version history. Checkpoints (X-OpenCanvas-Checkpoint: 1) are the saves to keep if you prune; named and restore saves (X-OpenCanvas-Autosave: 0) always are.
  • At-least-once commit with idempotency key; final commit before room close; on graceful shutdown all dirty rooms commit.
  • Nothing is retained after the room closes and TTL passes.
  • Role changes you make during a session take effect only when you call the role API or the token expires — tokens are the contract.

8a. Ephemeral storage (no file storage of your own; ADR-043)

For hosts with nowhere to keep files, such as a meeting app:

[[host]]
id = "meet"
name = "Meeting"
jwt_secret = "env:MEET_JWT_SECRET"
api_key = "env:MEET_API_KEY"
storage = "ephemeral"          # default "host"
# template = "meeting"        # optional: a built-in template id, or a path to an .ocanvas or Markdown file
                               # unset: every canvas starts blank
# callback_base = "https://meet.example/api/opencanvas"   # optional: mentions and members only
  • No load and no save. The room starts blank, or from template, applied once by the server (people joining together never get it twice); no GET/PUT /files/{id}, no commit outbox. The editor gets session.storage = "ephemeral" and the save status {"t": "temporary"}. The editor shows "Not saved · temporary", skips the template picker and shows no host name. The commit API answers clean.
  • template ids: the 40 built-in templates (meeting, standup, retro, oneonone, brainstorm, allhands, …). An unknown id stops the server at startup and lists the valid ones.
  • Destroyed when the room closes: the last person leaves and OC_ROOM_IDLE_MS passes, or you call DELETE /v1/files/{fileId}/session. The server then deletes the WAL, snapshots, outbox and notification rows, sessions, uploads, the epoch row and the Redis keys of the room. Nothing is kept. Tickets stop working.
  • DELETE /v1/files/{fileId}/session closes the room at once: clients get {"t": "closed", "reason": "This canvas ended with the meeting"} and close 1000. Call it when the meeting ends.
  • A restart or deploy keeps it. A draining node tells clients to reconnect and leaves the canvas in storage; it reopens as it was.
  • A short reconnect inside the idle grace (a dropped network, a page reload) finds the canvas as it was. After the grace, launching the same fileId starts a new canvas.
  • Uploads are kept with the room (as in WOPI mode) and destroyed with it.
  • Export and download stay available, subject to export_formats and the token's perms.
  • Mentions and the members callback are used only when callback_base is set.
  • Wording ([host.flags] temporary_wording, ADR-049). "meeting" (default) says the canvas is deleted when the meeting ends and, at the end, "This canvas ended with the meeting". "room" is for a chat room that outlives each canvas: "This canvas isn't saved anywhere. It's deleted after everyone has closed it; download a copy to keep it.", the pill tooltip "Not saved anywhere. Deleted after everyone closes it.", the ended screen "This canvas ended when everyone left" with a Start a new canvas button (posts UI_StartNew; your page opens a fresh canvas), "You're no longer in this room, so this canvas is closed" when access is removed, and "You can view this canvas. Room moderators can edit." for viewers. The session answer carries "wording". Other values stop the server at start-up.

Your users must export to keep anything. Tell them so in your UI.

8b. Matrix rooms (Element widget)

integrations/matrix/ adds a canvas to Matrix rooms as a room widget, like Etherpad or Jitsi widgets. A small bridge (Node 24, no dependencies) is the host:

  • The widget asks the Matrix client for an OpenID token (get_openid), and the bridge verifies it with the user's homeserver (/_matrix/federation/v1/openid/userinfo). The homeserver is resolved by the Matrix server-name rules, and any private address is refused. URL template variables such as $matrix_user_id are never trusted.
  • A bot account checks that the user is joined to the room and that the widget points at the bridge. Power level ≥ state_default gives edit; everyone else gets a configurable role.
  • It mints a launch token (§3) for an ephemeral host (§8a): one canvas per widget. The canvas id is a hash of the room and widget ids. The user id is the Matrix id; the name is the room display name.
  • When someone leaves or is banned, the bot calls the role API (§7, role: "none").
  • The host sets frame_ancestors to the Matrix client origins (§4) and [host.flags] temporary_wording = "room" (§8a); the widget page reloads itself on UI_StartNew.

Verified in Element Web against Synapse: OpenID, membership, a non-member refused, two people co-editing, Matrix names, access closed on leave. Install, configuration and limits (not end-to-end encrypted, temporary only): integrations/matrix/README.md.

8c. Mattermost (plugin as the host)

integrations/mattermost/ is a Mattermost plugin (com.casualoffice.opencanvas) that is a full JWT-mode host: canvases live in channels (/canvas new, /canvas notes, a card in the channel, the editor in the right-hand panel), files go to Mattermost's file store, access follows channel membership, and leaving a channel calls the role API with none. Install and settings: integrations/mattermost/README.md.

[[host]]
id              = "mattermost"
name            = "Mattermost"
mode            = "jwt"
jwt_alg         = "HS256"
jwt_secret      = "env:MM_OC_SECRET"
api_key         = "env:MM_OC_API_KEY"
callback_base   = "https://chat.acme.example/plugins/com.casualoffice.opencanvas/oc"
allowed_origins = ["https://chat.acme.example"]

What a plugin host must know about Mattermost:

  • ServeHTTP receives the path without {subpath}/plugins/{id}, but v2 signs the full path: the plugin puts the prefix back before checking.
  • Mattermost removes Authorization before a plugin sees the request: read the callback token from X-OpenCanvas-Callback-Token (§5).
  • Mattermost re-encodes the query string (keys sorted), so the members call arrives as ?limit=…&q=… although ?q=…&limit=… was signed: the plugin accepts the same pairs in any order.
  • Mattermost sends no frame-src, so the canvas frame needs no CSP change there.
  • The plugin puts "start": "page" in every launch token (§3): its create dialog already asked for the kind, so new canvases open on the page, not the template picker. Its panel listens for Error SESSION_CLOSED to offer Reopen.

Tested end to end against Mattermost 12.1.0 (README "Status").

9. Checklist for integrators

  • Register host, share secret/API key out of band.
  • Backend endpoint that signs the launch JWT after your ACL check.
  • Implement load / save (+ assets). People: give user.detail in the token; add members (≤ 500) and/or GET /files/{fileId}/members (docs/21); call the role API or members/invalidate when access changes.
  • Verify X-OpenCanvas-Signature on callbacks.
  • Add OpenCanvas origin to your CSP frame-src; add your origin to our allowed_origins.
  • Handle 409 (we save a copy or reload, per your policy). With copy, implement POST /files/{id}/copies; editors are told the new file's url and the session turns read-only. With reload, the session's unsaved changes are dropped and everyone reconnects onto your version.
  • Call the role API when ACLs change.
  • Try examples/sample-host end-to-end before going live (WOPI hosts: examples/wopi-host and scripts/e2e-wopi.sh).
