Architecture

3. Key flows

3.1 Open (JWT launch mode)

Host backend        Browser (host page)          OpenCanvas            Host callbacks
     │ sign JWT{file,user,role,perms,cb}  │                    │                      │
     │──────────────────────────────────▶│                    │                      │
     │                 │ iframe POST /launch (token) ─────────▶│ verify sig, exp, aud │
     │                 │                                      │── GET file ─────────▶│ (if room not live)
     │                 │                                      │◀─ .ocanvas bytes ────│
     │                 │                                      │ load into room       │
     │                 │◀─ editor HTML + session cookie/ticket │                      │
     │                 │── WSS /collab/{room}?ticket ─────────▶│ sync step1/2, awareness
  • If the room is already live (another user editing), the server does not re-fetch the file — the new user joins the live CRDT. This is how Collabora/Loop behave and avoids fork-on-open.
  • The JWT is used once; the browser gets a short-lived, single-room session ticket for the WebSocket (ADR-005).

3.2 Open (WOPI mode)

Identical, except step "verify" is GET {WOPISrc}?access_token=… (CheckFileInfo) → role from UserCanWrite / UserCanComment / ReadOnly, and file is fetched with GetFile. Saves use PutFile with X-WOPI-Override: PUT and X-COOL-WOPI-Timestamp-style conflict detection (LastModifiedTime).

3.3 Edit

  1. Client applies change locally (instant), produces a Yjs update.
  2. Sends sync:update over WS.
  3. Room engine: role check (edit role; comment role may only touch the comments subtree) → apply to server Doc → append to room_updates (durable tail) → fan out to all peers (local + other nodes via bus if viewers are spread).
  4. Awareness (cursor, selection, pointer, colour, name) is ephemeral — never stored, fan-out only, throttled to 20 Hz.

3.4 Commit

Triggers: manual "Save version", autosave interval (default 60 s with changes), idle (30 s without edits), last user leaves, session close API, graceful shutdown.

room-engine ──(dirty since last commit)──▶ commit-engine
  serialize Doc → .ocanvas (zip: document.json, ydoc.bin, manifest.json)
  POST host save callback  (If-Match: last host version)
    200 → record host_version, clear dirty, emit "saved" to clients
    409 → host changed file outside session → emit "conflict" →
          policy: (a) save-as-copy callback, or (b) reload host version
          and merge as a new branch, per host config
    5xx/timeout → outbox retry with backoff; UI shows "saving… retrying"

Commits are at-least-once with an idempotency key (commit_id = ULID) so hosts can dedupe.

3.5 Preview / download

  • GET /preview?token=… → server fetches file (or uses live room state if live=1 and room exists), renders static HTML via render. No WS, no Yjs on the client — fast and cacheable by (file_id, host_version).
  • GET /export/{format}?token=… → same source, renders MD/HTML/PDF/DOCX/PNG. PDF via headless Chromium pool optional sidecar; fallback to HTML print.

3.6 Close / cleanup

After final commit succeeds and no clients remain for ROOM_TTL_SECS (default 10 min): drop room from memory, delete room_updates and snapshot rows. Nothing about the document remains on our side (Principle 3).

Why keep snapshot + tail at all? So a node crash or deploy never loses an acknowledged edit that has not been committed yet. It's a write-ahead log, not storage.

Database selection (ADR-004): DATABASE_URL unset → sqlite://./data/opencanvas.db (WAL mode). mysql:// → MySQL 8 / MariaDB 10.6+. Same migrations, sqlx Any driver, portable SQL subset. **Cluster without DATABASE_URL** (REDIS_URL set): every row above lives in Redis instead, behind the same store interface (§5.2.2, ADR-030).

5. Scalability model

5.1 Single node (default)

SQLite + in-process rooms. Handles thousands of connections. Zero dependencies.

5.2 Cluster (MySQL/MariaDB + Redis)

             ┌───────── L7 load balancer ─────────┐
             │ HTTP: round-robin                  │
             │ WS: hash(room_id) → node (sticky)  │
             └───────┬──────────┬──────────┬──────┘
                   node-1     node-2     node-3   (identical binaries)
                     │  owns rooms by lease   │
                     └──── Redis (leases) ─ internal WS relay ┘
                     └──── MySQL/MariaDB (snapshots, tails, outbox) ────┘
  • One owner per room (ADR-006). The owner holds the authoritative Yrs Doc in memory. Ownership is a Redis lease (SET room:{id}:owner node NX PX) renewed every 5 s.
  • If the LB routes a client to a non-owner, that node relays the connection to the owner over one internal WebSocket per client connection (/v1/internal/relay/:room, HMAC-signed with OC_CLUSTER_SECRET, the grant forwarded signed). Per-connection order is TCP order; the owner treats the relayed connection like a local one and enforces roles. Clients never need to know. Host-API room calls (patch, commit, role, close, state for exports) on a non-owner are forwarded to the owner (POST /v1/internal/rooms/:room, same signature).
  • Owner dies → its relays break; the edge node probes the owner's /healthz and, if the process is gone, takes the lease over with a compare-and-set on the dead owner's value (otherwise the lease expires after 15 s). The new owner loads snapshot + WAL from the DB and continues; clients are told reconnect (1012) and resync in well under 5 s. Unacked client updates are resent by the Yjs client on reconnect (Yjs sync is idempotent). A node whose renewal finds another owner steps the room down (clients reconnect, no save).
  • Fencing (docs/22 §8 weakness 3). A lease alone cannot stop a node that was paused past its TTL from writing before its next renewal. Every room actor takes the room's next epoch from the database (room_epochs, bumped in one transaction) as it loads, with the lease held and before it reads the WAL. WAL appends are a single guarded INSERT … SELECT … FROM room_epochs WHERE room_id = ? AND epoch = ? per room batch (one SELECT per row joined with UNION ALL, so a stale batch is refused whole); snapshots, outbox rows and the closing purge start their transaction with UPDATE room_epochs … WHERE epoch = ? (row lock). A write with an older epoch changes nothing and the actor stops at once: no fan-out, no save, clients get 1012 and reconnect to the new owner. The same holds on SQLite and MySQL/MariaDB, and with Redis lost (the epoch lives in the database).
  • An update is fanned out only after its WAL append succeeded. Updates that queue while a room's append runs are written as one batch (a row and seq each), then fanned out in order; anything that reads the doc's state (sync step 1, joins, exports, patches, saves) writes the pending batch first. On SQLite one writer task commits many rooms' batches per transaction (group commit). A failed append (after deadlock retries) closes the room with 1012 and no save: the next actor rebuilds from the WAL and clients resend what it lacks. Deadlocks (1213) and lock waits (1205) are retried 3 times with jittered backoff (25-50 ms, 50-100 ms); a save never goes to the host without its outbox row.
  • The outbox sweeper claims a row (claimed_by, claim_until) and the room lease before resuming it, so two nodes never resend the same commit.
  • SIGTERM drain: /readyz turns 503, WebSocket upgrades are refused with 503 + Retry-After: 5 (before the upgrade), refuse new rooms, commit dirty rooms, {"t":"reconnect"} + close 1012 to every client (local and relayed), release leases, exit.
  • REDIS_URL with SQLite refuses to start (SQLite is single-node only). REDIS_URL without DATABASE_URL is Redis-only storage (§5.2.2).
  • Stateless HTTP (launch/preview/export) scales horizontally with no coordination. Export rendering can be split into a worker pool.
  • Large rooms: viewers can be fanned out by non-owner nodes from a Redis channel, so a 500-viewer room does not saturate one node.

5.2.2 Redis-only cluster (ADR-030)

A cluster needs only Redis: with REDIS_URL set and DATABASE_URL unset, the store keeps all server state in the WAL Redis; with DATABASE_URL set, the database is used exactly as above.

stateRedis-only
room snapshot (periodic sync target, 5 s / 500 updates, close, drain)hash oc:snap:{room}
WALstream oc:wal:{room} (as §5.2.1)
fencing epochoc:epoch:{room}, authoritative: INCR per claim, the clock in ms when missing
commit outboxhash oc:ob:{id} + zsets oc:obroom:{room}, oc:obpending; id = idempotency key; claim lease claimed_by/claim_until
mention outboxhash oc:nt:{id} + zset oc:ntdue
sessionshash oc:sess:{ticket} (TTL = ticket expiry + 1 h) + zset oc:roomsess:{room}
used launch jtiSET oc:jti:{host}:{jti} NX EX
room rows, WOPI assetsoc:room:{room}, oc:rooms; oc:asset:{room}, oc:assetm:{room}, oc:assetrooms

Guarded writes (outbox insert, snapshot + stream trim, closing purge, WAL append) are single Lua scripts that check the writer's epoch first, so fencing works as with the database. One Redis primary (standalone or Sentinel), not Redis Cluster.

Redis loses its data (restart without AOF, flush, failover to an empty replica):

  • with SQL: an append that finds no epoch key restores it from room_epochs and retries; the current owner keeps writing, a stale writer is still refused. Rooms are no longer all fenced. WAL entries since a room's last DB snapshot exist only in the owner's memory until its next sync.
  • Redis-only: there is nothing to restore from. oc:instance (set once, checked every 2 s) is missing, and every node logs REDIS LOST ITS DATA at ERROR. Rooms are fenced at their next write, close with 1012 and rebuild from the host's last saved file plus what reconnecting clients resend. Pending commits and sessions are gone (clients relaunch); edits of clients that do not come back are lost. Hence appendonly yes is required in production.

5.2.0 Durability modes (ADR-029)

  • **OC_DURABILITY=memory** (default without Redis): the room's Y.Doc lives in memory; an update is acknowledged (fanned out on the next 40 ms tick) right after the in-memory apply, with no database write. The encoded state is dumped (epoch-fenced) to room_snapshots every OC_DB_SYNC_MS (2 s) while it changes, before each host save, on drain and on close. After a crash the room loads the last dump; clients that reconnect resend newer edits (Yjs sync step 1/2). **Edits from the last ≤ OC_DB_SYNC_MS before a crash are lost only if no client that holds them comes back.**
  • **OC_DURABILITY=wal**: the strict path below (§5.2.1): acknowledged means in the WAL.
  • With a Redis WAL configured: §5.2.1's hot WAL in Redis, whatever OC_DURABILITY says.
  • Idle eviction: a room with no peers and nothing unsaved for OC_ROOM_IDLE_MS (60 s) is saved, purged and dropped from memory.

5.2.1 Write path: batches, outbound tick, hot WAL in Redis (ADR-028)

  • A room applies updates as they arrive and queues them. At most every 40 ms (armed by the first queued item) it appends the queue as one batch, then sends one merged update frame and one presence frame shared by every peer. Nothing is fanned out before the batch is durable; a failed append closes the room with 1012 and fans nothing out.
  • Without Redis the WAL is room_updates in the database (one guarded multi-row insert per batch; on SQLite one writer task commits many rooms' batches per transaction).
  • With Redis (OC_WAL_REDIS_URL, default REDIS_URL) the hot WAL is one stream per room, oc:wal:{room}, appended by a Lua script that checks the epoch mirrored at oc:epoch:{room}; the database gets a snapshot every OC_DB_SYNC_MS (5 s) or 500 updates and on close/drain, and the stream is trimmed only after that snapshot commits. Recovery: DB snapshot + stream entries after it.
  • Durability contract. An edit is acknowledged (fanned out) once the WAL store has it: the database, or Redis when configured. With Redis AOF appendfsync always a Redis crash loses nothing acknowledged; with everysec, up to about 1 s; with AOF off, up to the last DB sync. Run Redis with appendonly yes and appendfsync always (or everysec plus a replica, accepting ≤ 1 s). The server warns at start-up otherwise (docs/13).

5.3 Capacity math (2 vCPU node)

  • Yrs apply + broadcast ≈ 10–50 µs per small update; 300 rooms × 10 upd/s = 3 000 upd/s ≪ capacity. Bottleneck is fan-out bytes, not merge.
  • Memory: ~ 3× doc size per live room; 300 rooms × 1 MB × 3 ≈ 900 MB worst, typical 100–200 MB.

6. Security architecture (summary — detail in 07)

  • Per-host keys; JWT aud, iss, exp ≤ 10 h, jti replay cache.
  • Role enforced server-side per frame; client UI is advisory only.
  • Embeds rendered in sandbox iframes from an allow-list; user HTML never rendered unsanitised; CSP frame-ancestors = host origins.
  • Unfurl fetcher: DNS-pinned, private-IP block, size/time caps.
  • No document content in logs; PII limited to display name/avatar in memory.

7. Deployment

  • Docker image (distroless, ~20 MB) + docker-compose.yml (single node, SQLite) + docker-compose.cluster.yml (3 nodes, MariaDB, Redis, nginx).
  • Helm chart (P2). Config via env vars + optional opencanvas.toml.
  • Graceful shutdown: stop accepting, commit all dirty rooms, release leases.
