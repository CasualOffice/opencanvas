Capacity and sizing

Status: first measurement, 2026-11-22 (PERF-01); worst case, crash recovery and cluster correctness added the same day (PERF-02, §8–§13; read §8's weaknesses before sizing a cluster). Laptop numbers: indicative, not a guarantee. Rerun on your own hardware with scripts/bench.sh (below).

1. Machine and method

  • Machine: Apple M4, 10 cores, 16 GB RAM, macOS 26.3. The server, the load generator and the mock host all ran on this one machine, over loopback. The load generator used up to 2.2 cores (one room of 550) and 0.6 cores (5,000 connections) next to the server, so the server never had the machine to itself.
  • Server: opencanvas release build from main (7e2de05), SQLite (DATABASE_URL=sqlite://…), OC_KEK set, OC_LOG=info, default limits and autosave (2 s debounce, 10 s max).
  • Load generator: crates/oc-bench (Rust, tokio, tokio-tungstenite, yrs). For each virtual user it mints an HS256 launch token for a bench host, POST /v1/launch, GET /v1/sessions/<ticket> and opens /v1/collab/<room>, like the SPA. The bench host's load and save callbacks are served by a mock inside the load generator that answers at once, so the host never limits a run.
  • Behaviour: editors type 3–6 chars/s in bursts of 3–10 s with about 60 % duty, move their caret (awareness), and on about 6 % of keystrokes edit a database cell and on 2 % drag a board shape (10 moves at 20 Hz). Like the editor, each client sends at most one update frame and one awareness frame per 50 ms window. Viewers only receive. Mix: 20 % editors / 80 % viewers.
  • Document: a Rust rebuild of the "Sprint 42 planning" demo canvas (same blocks, the 7-row database, a 12-shape board, one comment thread, a 40 KB inline image): 49 KB encoded Yjs state. big adds a 1,000-row database and a 500-shape board: 408 KB (oc-bench sizes).
  • Latency: every update frame an editor sends is logged by (client id, start clock, time); probe clients (4–10 per room) decode each update they receive and look it up. The figure is editor frame sent → peer received: server apply, WAL append, fan-out and both sockets. The client's own ≤ 50 ms batching window comes on top.
  • Server resources: ps (RSS, CPU time → CPU %, threads), lsof (open fds) and /metrics once per step. CPU % is per core: 100 % = one core busy. Each step ramps clients in, waits 5 s, then measures for 60 s (scenario C: 5 s).

3. What limits first

  1. Memory, in many-room deployments: about 0.2 MB per connection plus 5–14× the document per open room. Rooms stay in memory for OC_ROOM_TTL_SECS (600 s) after the last client leaves.
  2. Fan-out CPU and bandwidth, in big rooms: frames out = (editor updates + awareness) × peers. A 550-user room with 110 typing editors took 1.8 cores and 65 MB/s (520 Mbit/s).
  3. File descriptors: one per connection plus 25–45 (measured fds = connections + 25 to 42). Set ulimit -n (or the container's nofile) above the connection target.
  4. The per-room actor (one task per room applies, logs and fans out every update in order) did not limit anything measured: p95 6.8 ms at 550 peers.
  5. Latency stayed far under the 150 ms target everywhere (worst p95 10.2 ms, worst p99 24 ms). Rare outliers grew with load (max 760 ms at 5,000 connections); not investigated yet.

Not limiting on this machine: threads, the 550 room cap's own overhead, SQLite (B wrote about 3,000 WAL rows/s with no errors; see §6 for what was not measured).

4. Sizing for self-hosters

In short: up to 1,000 concurrent users on 1 vCPU and 512 MB; up to 5,000 on 2 vCPU and 2 GB; beyond 5,000, cluster mode.

Rules of thumb (keep ≤ 60 % of what was measured):

  • Memory ≈ 50 MB base + 0.25 MB per concurrent user + 5–14× the document size per open room.
  • CPU ≈ one core per 5,000 users in small rooms (20 % typing); one big room of 550 needs about 2 cores on its own (measured 1.8).
  • Bandwidth out ≈ 1.1 KB/s per typing editor per peer in the room (B: 4.46 MB/s for 1,000 editors with 4 peers each; A: 65 MB/s for 110 editors with 549 peers each).

7. Findings for the server

Fixed 2026-11-22 (branch perf-revocation-fanout)

Measured on the same M4 laptop, but not idle: another session was running Docker cluster benchmarks (load average 14–22 on 10 cores), so CPU and latency below are noisy. Every number comes from oc-bench with the same arguments as §2, run back to back against a release build of main (79fa518) and of the branch, on ports 8901/8902.

  • Memory per idle connection: 0.20 → 0.087 MB (−57 %). Root cause: tungstenite's read buffer. Its default read_buffer_size is 128 KiB and the codec zero-fills the buffer up to its capacity on the first read (FrameCodec::read_in: in_buffer.resize(capacity, 0)), so every connection kept 128 KiB resident. routes::collab::ws_config now sets an 8 KiB read buffer on client sockets and the cluster relay (a larger frame still grows the buffer, up to the frame limit). Guard: collab::tests::websocket_read_buffer_stays_small.

Left: the rest scales with the document (0.087 MB with the 49 KB demo doc, 0.026 MB with an empty one). Likely cause, not verified with a heap profile: tungstenite's write buffer (out_buffer, a Vec that never shrinks) keeps the capacity of the largest frame sent, which is the initial sync step 2 (the whole document). The WebSocket config has no setting for this, so a fix would mean sending the initial state in chunks or a patched writer.

  • Fan-out shares one buffer. Outbound::Frame now carries bytes::Bytes; broadcast clones a reference per peer instead of to_vec() per peer, and the relay forwards the owner's frames without a copy. Wire format unchanged. Test: tests/rooms.rs fan_out_shares_one_buffer_between_peers (two viewers get the same allocation; failed on main). Scenario A at 550 (20 % editors, 60 s), one step:

  • Revocation in a cluster (docs/21 note 3): the members cache and revoke set are still per node, but every revoke, restore and invalidate is now published on Redis pub/sub (oc:members, HMAC-signed) and applied by every node within a second. Tests: tests/cluster.rs revoke_on_one_node_reaches_every_node (+ …_over_redis with OC_TEST_REDIS_URL).

Still open

  • Room memory is 5–14× the document, not the "~3× doc size" in docs/03 §5.3; docs/03's 300-room estimate is low for database/board-heavy documents.
  • **/metrics lists fewer series than docs/13 says.** The server exports oc_rooms_active, oc_connections_active, oc_launches_total, oc_updates_total, oc_saves_total and a few error counters; oc_update_apply_seconds, oc_fanout_bytes_total, oc_commit_seconds, oc_host_callback_seconds, oc_wal_bytes and oc_room_doc_bytes do not exist yet, so save latency here was measured at the mock host.
  • §2–§4 still show main's numbers (0.20 MB per connection). With the read-buffer fix the per-user memory rule of thumb in §4 is conservative; update it after a clean rerun of B and C.

8. Worst case, crash recovery and cluster correctness (PERF-02, 2026-11-22)

Same machine as §1 (Apple M4, 10 cores, 16 GB, macOS 26.3); server from main at 55c969f, release build. MariaDB 10.11 and Redis 7 ran in Docker Desktop on the same laptop. Every result below is from a real run; raw JSON and Markdown are written to target/bench/ by the commands in §13. Server source was not changed: bugs are reported with the command that reproduces them.

Weaknesses found

  1. A room of 550 with everyone typing cannot keep up (S1). The room actor spends 85 % of its time in on_awareness → fan_out_awareness → rewrite_for, which parses and re-serialises each awareness JSON once per peer. It applies about 290 updates/s against about 2,500 offered: latency grows by about 0.9 s every second (p95 638 s after 12 minutes), RSS grows about 70 MB/min, and autosave stalls (2 host saves in 12 minutes).
  2. The single-node SQLite WAL path tops out at about 5,900 appends/s, then degrades (S2). At 1,000 rooms × 5 with everyone typing (13,300 updates/s offered), 90 % of SQLite time was in sqliteDefaultBusyCallback sleeping on the writer lock (8 pooled connections). Throughput fell to about 2,000/s after 6 minutes, p95 reached 521 s, autosave lag p95 255 s. Throughput FIXED, latency still FAIL (2026-11-22, §9.3). Per-room WAL batches, a 40 ms outbound tick with one merged frame, SQLite group commit, and an optional hot WAL in Redis. S1 (550 typing) now applies all ≈ 2,750 updates/s at p95 ≤ 81 ms; S2 applies all ≈ 25,000 updates/s with 0 drops; p95 is 215–410 ms with the Redis WAL and MariaDB as the sync DB (PASS at 700 ms), but 1.2–1.6 s on SQLite alone and 0.19–1.33 s with Redis + SQLite (FAIL).
  3. A frozen node writes after it lost its rooms: two writers per room (K2). After a 20 s SIGSTOP (longer than the 15 s lease), the resumed node appended WAL rows for 20 rooms that another node had claimed, until its 5 s renewal noticed. There is no fencing token. Both nodes then failed WAL appends with Duplicate entry on (room_id, seq) (986 + 1,539 errors over 31 s). **FIXED 2026-11-22 (branch fix-fencing-wal-drain).** Fencing epochs: each room actor takes the room's next epoch from the database (room_epochs, migration 0006) before it reads the WAL; appends are one guarded INSERT … SELECT … WHERE epoch = ?, snapshots, outbox rows and the closing purge hold the epoch row first. A stale writer's first write changes nothing and its room closes with 1012 (docs/03 §5.2). Evidence: tests/durability.rs epoch_1_writes_are_refused_once_epoch_2_owns_the_room (run on SQLite and on MariaDB 10.11) and stale_owner_stops_at_its_first_write_and_clients_get_1012, both seen failing before the fix. K2 rerun 2026-11-22 (§11.1): PASS. The stale node was fenced at its first write within about 1 s of SIGCONT; 0 duplicate-key WAL errors, 0 WALSEQ refusals, 0 of 71,536 acknowledged edits lost, 20 rooms closed with 1012 and every client back within 288 ms. Same result with node 2 in Docker under docker pause and under a network partition (KD, 0 of 81,754 lost). Caveat: with REDIS_URL set the hot WAL is always in Redis (OC_WAL_REDIS_URL defaults to it and an empty value falls back), so in cluster mode the MariaDB WAL guard (INSERT … SELECT … WHERE epoch = ?) is not exercised: room_updates held 0 rows in every cluster run. The fencing that worked here is the Redis APPEND script's epoch check plus the guarded outbox/snapshot writes in MariaDB.
  4. A failed WAL append still acknowledges the update. Room::accepted logs WAL append failed and fans the update out anyway (crates/oc-server/src/room/actor.rs, accepted). Peers see the edit, but it is not durable until the next compaction or save. In K2 this lasted 25 s for 20 rooms. No acknowledged edit was lost in these runs only because clients resent their state. FIXED 2026-11-22. The update is fanned out only after its append succeeded; otherwise the room closes with 1012 and no save, and clients resend onto a room rebuilt from the WAL. Host patch calls get 503 ROOM_UNAVAILABLE. Evidence: tests/durability.rs failed_wal_append_is_not_fanned_out (the WAL table is renamed away mid-session; the peer never sees the edit, the sender resends it after reconnecting), seen failing before the fix. Seen under chaos 2026-11-22 (§11.1): in the KD partition 53 Redis appends failed and every one closed its room (storage error) instead of fanning out; 0 of 81,754 acknowledged edits lost. In K, 60 appends failed while Redis restarted, same outcome.
  5. MariaDB deadlocks (1213) are not retried. After a restart with many recovered rooms (mR) and during cluster chaos (K), these failed with Deadlock found … try restarting transaction: compaction failed (35), writing the commit outbox failed, marking commit done failed, and room load failed. The server logs them and moves on. An outbox row that is never written or never marked done weakens the outbox's crash guarantee. FIXED 2026-11-22. store::retry_with: 3 attempts, jittered backoff 25-50 ms then 50-100 ms, for 1213 / 1205 (and SQLite busy), around compaction, outbox write, outbox mark done, room load (epoch claim, room row, outbox rows, WAL read, purge, put) and WAL appends. A save is no longer sent without its outbox row: the save fails loudly (save not started, oc_save_errors_total, save_error status) and retries with the save backoff. Evidence: store::tests::transient_errors_are_retried_up_to_three_attempts (seen failing) and deadlocks_and_lock_waits_are_transient. mR rerun 2026-11-22 (§10.1): data PASS, deadlocks not fully gone. Two runs, 0 acknowledged edits lost in both. Run 1: 86 retries, **9 compaction failed with 1213 after all 3 attempts** (all within 50 ms, 30 s after restart, when 200 recovered rooms compact together); run 2: 62 retries, 0 left. Compaction runs again on its next interval, so nothing was lost, but the retry budget is not enough for that burst. The InnoDB deadlocks captured in run 2 are all insert-intention waits on gap locks: INSERT INTO rooms, INSERT INTO room_epochs, INSERT INTO room_snapshots (compaction deletes then inserts) and INSERT INTO commit_outbox (index ix_outbox_status). Likely fixes, not tried: upserts (INSERT … ON DUPLICATE KEY UPDATE) instead of delete-then-insert or check-then-insert, more attempts for compaction, or READ COMMITTED for these transactions. Repro: scripts/bench.sh mR, then grep '"level":"ERROR"' server-*.restart.log | grep -c Deadlock. scripts/bench.sh mR prints deadlock errors left after retries and the number of retries. The missing WAL latency metric is added: oc_wal_append_seconds (histogram, docs/13; wal_append_latency_is_a_histogram).
  6. MariaDB runs are sensitive to the database's own state. The same 1-node load gave p95 1.9 s at 1,000 connections right after the K2 cluster run on the same container (database dropped and recreated), and p95 9 ms on a fresh container (§12). After a crash, rooms reopen about 10× slower than on SQLite (p95 533 ms vs 59 ms, WAL replay plus row reads over the Docker network). This setup (Docker Desktop on macOS) is not a production database; the server has no metric for WAL append latency (oc_commit_seconds in docs/13 does not exist yet), so an operator cannot see this happening.
  7. A draining node accepts WebSocket upgrades and then closes them (join failed: server is draining, 8,760 in about 10 s on one node in K). Clients that reconnect to the same address loop until a load balancer removes the node. FIXED 2026-11-22. While draining, GET /v1/collab/:room answers HTTP 503 with Retry-After: 5 before the upgrade (and /readyz is 503). Evidence: tests/http.rs draining_node_refuses_websocket_upgrades_with_503, seen failing before the fix (the upgrade was accepted). K rerun 2026-11-22 (§11.1): PASS. During the rolling restart the verified clients got 211 HTTP 503 refusals (178 from bench-1, 33 from bench-2, 0 from bench-3) and 0 accepted-then-closed upgrades (join failed: server is draining: 0; it was 8,760 before the fix). Another 175 connects were refused at TCP level while a node was down between stop and start.
  8. Three nodes held less load than one on this laptop (T). With a room's clients spread over the nodes, 3 nodes hit p95 9.8 s at 5,000 connections, where 1 node held p95 8.9 ms. The same thing happened in two separate runs. It is not CPU-bound and not root-caused (§12).
  9. Minor: after an owner moved, relayed peers of the 550 room were refused with room full (435 times), apparently because old slots still counted. Not root-caused. In the load generator, two of 550 clients in one room never got role (connect p95 90 s under S1's overload).

9.3 Batched WAL, outbound tick, hot WAL in Redis (PERF-04, 2026-11-22)

Branch perf-wal-group-commit (ADR-028; design in docs/03 §5.2.1):

  1. Per-room batches. Updates are applied as they arrive and queued; the queue is appended as one batch (a row and seq per update; one epoch-guarded statement, or one Lua script on Redis; all or nothing) and only then fanned out. Anything that reads the doc's state writes the queue first.

12.1 Why one laptop cannot show scale-out, and the multi-machine recipe (PERF-06)

Not rerun on purpose. On one machine the three nodes, the load generator, its mock hosts, Redis and the database share the same 10 cores, memory bandwidth, loopback and (for MariaDB) one Docker VM. Adding a node adds no hardware, only work: about 60 % of sockets are relayed (every relayed update crosses loopback twice and is framed on two nodes), each node keeps its own Redis lease traffic and DB pool, and the load generator (57 % of a core at 5,000) competes with the nodes it measures. A cluster can only beat one node when each node brings its own CPU and network, so the single-laptop T result is an upper bound on relay cost, not a measure of scale-out.
