A live canvas inside your app. Your files stay yours.

OpenCanvas is a collaborative canvas you embed, the way apps embed Collabora: rich text, databases and whiteboards, with live cursors. Your application keeps the users, the permissions and the file. OpenCanvas does the editing, merges every change live, and saves the file back to you on its own.

How it fits

Your app decides. OpenCanvas edits.

Your backend checks who may open which file, signs a short launch token, and opens OpenCanvas in an iframe. From then on OpenCanvas runs the live session and calls your app back to load and save the file. Once a session is saved and idle, it keeps nothing.

  • Your app ownsSign-in, users, who can view, comment or edit, the file itself, its versions and its retention.
  • OpenCanvas ownsThe editor, real-time merge, cursors and presence, preview, export, and autosave back to your storage.
  • One serverA Rust binary with the editor built in. SQLite by default; MySQL or MariaDB and Redis when you run several nodes.
  • One embedAn iframe form POST, or the <open-canvas> web component, with events for ready, saved, presence and errors.
Why it matters

Three ideas, in plain words.

The names in the strip above are what let OpenCanvas sit inside someone else's product without taking over its data.

  • CRDT

    Edits that cannot collide

    Every change is a small update that merges with everyone else's in any order, the same way on every screen. The server orders and relays updates; it never has to resolve a conflict between two people typing.

    So: live co-editing without locks, and brief disconnects resync on their own.

  • Host callbacks

    The file never moves house

    OpenCanvas loads the file from your app when a session opens and writes it back with a plain HTTP call, signed so you know it is us. If your file changed elsewhere, your chosen policy runs: save a copy, or reload.

    So: your storage, versions and retention rules stay the only ones.

  • Autosave

    Nobody presses Save

    Changes save on a short timer, when the canvas goes idle, when the last person leaves and when the server shuts down. Each save is written to an outbox first, so a restart resends it rather than losing it.

    So: the status reads Saved, and that is true.

Alpha: what it is not yet

  • Early release, with no SLA. Release 0.2.0 has best-effort support, no production SLA, and fixes only on the 0.2.x line. The release notes list every limit and the upgrade steps.
  • Most work is built and verified but still awaits the owner's review; the roadmap marks each item.
  • Memory grows with the documents you keep open. While people type, a room's document takes many times its saved size in memory; memory is given back after rooms close. Size from the sizing guide.
  • Durability depends on the mode. Without Redis the default keeps rooms in memory and dumps them every two seconds: after a crash, the latest edits come back only from clients that reconnect. Use wal mode, or a Redis WAL with append-only persistence, when every acknowledged edit must be on disk; see operations.
  • Single node first. Cluster mode passes the crash and chaos runs, but scale-out across machines has not been demonstrated. A single SQLite server with a thousand busy rooms of nonstop typing in wal mode still falls behind by over a second.
  • Only the import and export formats in the release notes are tested.
  • Link cards show the site's name until the safe link-preview fetcher is built; server-rendered preview for viewers is not built yet. The Helm chart is linted and rendered in CI but not yet installed in a real cluster.
  • The assistant and MCP are experimental and off by default. They are phase 1 and await the owner's review. When an operator turns them on, canvas content is sent to the configured model server.

Every item is a row in the project's tracker, and the roadmap is generated from it.

Assistant

Ask, check the plan, then let it build.

Select some text and press ⌘J or Ctrl+J, or choose Ask Assistant. Say what you want. The assistant shows its plan first, and nothing changes until you run it. Then it builds in place while everyone watches: its own cursor, a label on what it made, and suggestions where it would change text that was already there.

  • Review what it didAccept or reject each suggestion inline, or all at once from the review bar.
  • Undo the whole runOne button removes everything the run added. Changes you accepted stay yours.

What it may do, in plain words

  • It acts as you, and only as youEvery change it makes passes the same server-side role check as your own typing. If you can only view, it cannot run; if you can only comment, it can answer and comment, not edit.Tested: viewer refused, commenter answer and comment only
  • Existing text gets suggestionsBy default, changes to what people wrote arrive as suggestions you accept or reject; new content is added directly. Your operator can change the default per app.Tested: suggest mode writes only to suggestions
  • Nothing before you approveThe run waits at the plan. Cancel it there and the canvas is unchanged.Tested: nothing before approval; cancel leaves nothing, over real sockets
  • Attributed and undoableIts edits carry the assistant's own identity, separate from yours, and Undo run removes them as one step.Tested: undo reverts the run's origin
  • Content goes only where your operator saysThe canvas text the assistant works on is sent to the model server your operator configures, and nowhere else: the Claude Platform, or a self-hosted model through vLLM, Ollama or llama.cpp. Browsers never call a model or see a key.Depends on your deployment: [ai.providers] in the server's OC_AI_CONFIG file, chosen per app in hosts.toml
  • Self-hosted models need tool callingThe server checks each model at start-up. A model that cannot call tools gets answer mode only; agent mode stays off for it.Tested: agent mode needs a tool-calling model

MCP for external agents

Agents outside the editor, such as your own backend or a desktop assistant, can read and edit a canvas through the Model Context Protocol endpoint, POST /mcp/{hostId}. Every change shows live to the people in the canvas.

Your app issues the tokens and OpenCanvas only checks them, with the same keys as launch tokens. A token's scopes can narrow what the user's role allows, never widen it. The endpoint is off until you turn it on. Tested: off by default; bad tokens refused; a scope narrower than the role wins

hosts.toml
[host.ai]
enabled      = true
provider     = "claude"     # a profile in [ai.providers]
default_mode = "suggest"    # for changes to existing text
mcp          = true         # POST /mcp/{hostId}; off by default
mcp_issuer   = "https://id.acme.example"

Integrate

Three steps to a live canvas in your app.

Register your app with the server, embed the editor with a token your backend signs, then answer a few HTTP callbacks. The code below is from the integration guide.

1. Register your host
# opencanvas.hosts.toml
[[host]]
id              = "acme"
name            = "Acme"
mode            = "jwt"
jwt_alg         = "HS256"
jwt_secret      = "env:ACME_OC_SECRET"
api_key         = "env:ACME_OC_API_KEY"
callback_base   = "https://api.acme.example/opencanvas"
allowed_origins = ["https://app.acme.example"]
2. Embed it with a signed token
<script type="module"
  src="https://canvas.example.com/sdk/embed.js"></script>
<open-canvas server="https://canvas.example.com"
  token="{{ jwt }}" theme="auto"
  style="height:100vh"></open-canvas>

// Your backend signs the token after its own ACL check:
// file, user, role (view | comment | edit), perms

3. Answer these callbacks from your backend:

  • GET /files/{fileId}Load: return the file and its version
  • PUT /files/{fileId}Save: store it, answer the new version, or 409
  • POST /files/{fileId}/assetsStore an uploaded image or file
  • GET /files/:id/membersPeople with access to the file, for @mentions
  • POST /files/{fileId}/copiesSave a copy when the file changed elsewhere
  • X-OpenCanvas-SignatureHMAC-SHA256 on every call, so you know it is us

Block SDK · v0.2

Build your own blocks.

An OKR tracker, a ticket card, a chart from your own service: write it once with @opencanvas/block-sdk. OpenCanvas runs it in a sandbox, keeps its data in the document, lets people edit it together and exports it. The code below is from the Block SDK guide.

1. Write the block
import { defineBlock, h } from "@opencanvas/block-sdk";

defineBlock<{ value: number }>({
  render(el, ctx) {
    const slider = h("input", { type: "range" });
    slider.addEventListener("change", () =>
      ctx.setAttrs({ value: Number(slider.value) / 100 }));
    el.append(slider);
  },
});
2. The host turns it on
# opencanvas.hosts.toml
[host.blocks]
enabled = ["oc.progress", "acme.okr@^1"]

[host.blocks.permissions."acme.okr"]
members = "none"   # narrow what it may read
  • SandboxedEach block runs in its own frame on a separate origin, with a strict content policy
  • CheckedManifests, hashes and schemas are verified; the server re-checks every change
  • LiveCo-editing, comments and roles work in custom blocks as in built-in ones
  • Never lostA missing or refused package shows its saved copy; the data stays in the file

Self-host

One container to start, more nodes when you need them.

A single node runs on SQLite with no database to set up. For many concurrent users, point several nodes at MySQL or MariaDB and Redis: each room has one owner node, and the others relay to it.

Single node, SQLite
docker run -p 8080:8080 -v oc-data:/data \
  -e OC_PUBLIC_URL=https://canvas.example.com \
  -e OC_KEK=$(openssl rand -base64 32) \
  -e OC_HOSTS_FILE=/data/opencanvas.hosts.toml \
  opencanvas/server:0.1

Questions people ask.

More in the documentation FAQ.

Can I use it in production today?

OpenCanvas 0.2.0 has best-effort support and no production SLA. Review the deployment limits before committing it to a production workflow.

What does the licence allow?

OpenCanvas is open source under the Apache License 2.0. You may use, modify, self-host, embed and redistribute it, in open or closed, commercial or non-commercial products. When you redistribute it, keep the NOTICE file. The LICENSE file has the exact terms.

Does OpenCanvas keep my documents?

Only while a session is live. The server keeps a snapshot and the recent updates so it can survive a restart and let late joiners catch up, and deletes them after the session is saved and idle. The file itself lives in your app.

How do users sign in?

They sign in to your app, not to OpenCanvas. Your backend checks access and signs a short-lived launch token naming the file, the user and the role; OpenCanvas trusts that decision for the life of the token and enforces it on every edit.

Can we use it in Jitsi Meet, like Etherpad?

Yes. Add one Prosody plugin and a few .env lines to your Jitsi deployment, with no Docker image or compose changes. Everyone in the meeting opens the same canvas from Shared document. The canvas is temporary: it starts blank or from a template you choose, nothing is stored, and it is deleted when the meeting ends, so people download what they want to keep. See Jitsi Meet.

We already use Collabora through WOPI. Can we reuse that?

Yes. OpenCanvas speaks WOPI as a client: discovery, CheckFileInfo, GetFile, PutFile and PUT_RELATIVE, with an allow-list for the WOPISrc it will call. See WOPI mode.

What can it export?

Markdown, HTML, JSON, its native .ocanvas, Word, and PDF when the operator runs the optional Gotenberg sidecar (otherwise the editor prints to PDF). Whiteboards export as SVG and PNG.
