Block SDK: chrome, fallbacks and insert

Every screen and state for third-party blocks in v0.2 (docs/27 §3, UI items §6.5 and §6.6), drawn at real sizes (desktop 1280 × 800, close-ups at 860 wide, phone 390 × 844). Nothing here is built; these are for approval before any UI code (ADR-011). Design: docs/27-ROADMAP-v0.2.md §3, ADR-040 and ADR-042 (Proposed).

The model in one line. A third-party block runs in a sandboxed iframe from a separate origin; OpenCanvas draws only the thin frame around it, its badge, its selection and focus, and, when it cannot run, a status line with the stored fallback.

Example blocks. acme.okr (OKR, an objective with key results) and acme.ticket (Ticket, a card from Acme Tracker), installed by the operator and enabled for the Acme Docs host, in the “Admin sign-in, Q4 plan” canvas. Magenta labels are review notes, not UI. All icons are Lucide.

Decisions for the owner
  1. Badge only on hover, focus and selection (1a, 1b), not always visible. Fallback states always show it.
  2. Focus inside a block: solid 2 px accent ring with a 2 px gap (1e), stronger than the editor’s 28% selection ring.
  3. One wording for “not installed”, “not enabled for this host” and “refused by integrity check” (2b).
  4. Crash loop guard: three crashes in a minute turns Reload block into “Try again later” for 30 s (2a).
  5. Comments anchor to the whole block; the block is not told about them (4a).
  6. The / menu group is called “From your organisation” and has no empty state; the gallery category does (6a, 6c, 6f).
  7. Gallery previews: a sketch drawn from the manifest, or an optional preview.png in the package (6e). This adds an optional manifest field.
  8. Menu group labels and item descriptions move from --fg-3 (about 3.4:1, below AA) to --fg-2 in the / menu and insert sheet. That changes the editor’s existing menus too.
  9. Per-host permission narrowing in [host.blocks.permissions] (7a), and refused packages in /healthz (7b). Both go a little beyond §3.3.

1 · A third-party block in a document BSDK-03 · §6.5

Two blocks from acme.okr and acme.ticket in an ordinary canvas. What is inside the thin frame is drawn by the block in its sandboxed iframe (with our theme tokens); everything on and around the frame is ours.

2 · Fallbacks: crashed, missing, newer BSDK-03 · BSDK-05 · §6.5

When the block cannot run, our chrome replaces the frame with a status line and the stored fallback (§3.2), drawn by the editor, never by the block. The data in the canvas is untouched in every case.

3 · Permissions and read only BSDK-03 · §6.5

What a block may do is the manifest’s request ∩ the operator’s config ∩ the host’s config (§3.2). People see the result, never the arithmetic.

4 · Comments on an SDK block BSDK-03 · §6.5

Text inside the frame is not in the editor’s document, so a comment anchors to the block as a whole, the way comments on a database or board do.

5 · Phone BSDK-03 · §6.5

Below 720 px there is no gutter and no hover. A tap selects the block and shows its badge; the badge opens a sheet. Targets are 44 px.

6 · Slash menu and insert gallery BSDK-03 · §6.6

Installed and enabled block types appear where people already look for blocks: the / menu, the phone insert sheet and a gallery. Same icon (the manifest’s Lucide name) and title everywhere.

7 · Operator view (documentation, not UI) BSDK-01 · §3.3

Blocks are installed by the operator and enabled per host (decision 5). There is no screen for this in v0.2; these frames show the config and logs the docs will describe, so the owner can check the words people will meet.
