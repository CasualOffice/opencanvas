Portable live blocks

Every v0.3 live block screen and state (docs/27 §2 and §6 items 1–4, deltas in docs/34 §2), drawn at real sizes (desktop 1280 × 800, close-ups 860 wide, host panels 560, phone 390 × 844). Nothing here is built; these are for approval before any UI code (ADR-011). Design: docs/27-ROADMAP-v0.2.md §2, docs/34-ROADMAP-v0.3.md §2, ADR-039.

The model in one line. A live block is a small host file embedded by reference and opened as its own room; its access is the file’s, never the embedding canvas’s. A reference (blockRef) is a read-only projection of a block in another canvas.

Example. The “Release 4.2 checklist” lives in Acme Docs under Product / Releases and is shown in the Sprint 42 planning canvas, the Leadership weekly canvas and #release-42 in Acme Chat. All icons are Lucide; magenta labels would be review notes, not UI.

Decisions for the owner
  1. A live block always shows a thin header (Live mark, title, source path, people, Open source, menu), unlike SDK blocks whose badge shows only on hover (2a). Reason: its access and its edits belong to another file.
  2. Green “Live” mark for live blocks, grey “Reference” mark and a sunken background for read-only references (2a, 3a).
  3. Presence inside a live block shows people from every place it is used, labelled with where they are (“Amara · in Leadership weekly”) (2b). This tells the canvas’s viewers the name of another canvas; the alternative is the name only.
  4. A one-time hint per person on the first edit: “Edits here change it in 3 places” (2b). Needs the host’s usage index; without it the hint has no count.
  5. “Who can see this” shows how many people with access to the canvas cannot open the live block (2d), from /access answers for the member list. Costs one host call per member per 30 s; off above 200 members.
  6. Paste of a block link asks Live block / Reference / Link, default Live block for a live file and Reference for an ordinary block (1d).
  7. Insert from the host’s own picker via UI_PickLiveBlock → Action_InsertLiveBlock (1e); OpenCanvas keeps no list of live files.
  8. “Convert to a copy” (unlink) is offered to anyone who can edit the canvas and read the live block (2f).
  9. References refresh automatically and flash once; no manual refresh button except in the menu (3b).
  10. Snapshot default stays “title” (5c); “none” hides even the title (5d).
  11. New webhook events live.embedded and live.removed so the host can answer “where is it used” (7a).

1 · Make live and insert LIVE-03 · §6.1

A live block is its own small host file, embedded by reference (ADR-039). “Make live” turns a selection into one; a pasted link or the host’s picker inserts one that exists. Both need the host’s optional POST /files callback and perms.live; without them the items are not shown.

2 · Live block chrome LIVE-03 · §6.2

Unlike an SDK block, a live block always shows a thin header: its content follows another file’s access rules, and edits land in that file. The header carries the source, who is in it, and the way out to the source.

3 · Block reference card LIVE-04 · §6.3

A blockRef shows a read-only projection of one block in another, ordinary canvas. The server renders it (the same projection as canvas_read) and refreshes it when the source changes. Nothing is copied into this canvas’s CRDT.

4 · Compact block view in a host LIVE-06 · §6.4

<open-canvas file="…" view="block"> renders one live file with compact chrome: no top bar, no gallery, height follows the content (UI_Resize). Hosts that cannot run the web component use GET /api/v1/files/{id}/render?format=html, read only.

5 · Failure states LIVE-02 · LIVE-03 · §6.2

Every state keeps the header shape so the page does not jump, says what happened in one sentence, and offers at most one action. None of them changes the canvas’s content.

6 · Phone LIVE-03 · LIVE-06 · §6.2

Below 720 px the header keeps the Live mark, the title and the options button (44 px target); the source path moves into the sheet.
